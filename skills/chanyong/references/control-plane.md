# 多 Skill 控制层

本文件只在非简单任务需要读取项目、组合多个 Skill、处理路由歧义或验收时加载。`chanyong` 始终持有目标、范围和最终一致性；专业 Skill 只完成被分配的阶段。

## 先形成最小 Task Contract

不要直接按原句关键词选 Skill。先在当前上下文中形成下面这些字段；普通任务无需把它们全部展示给用户：

```text
original_request：用户原文，精确保留
goal：用户最终想得到什么
artifact：页面、代码、图片、报告、商品资料或其他产物
operation：创建、修改、审查、研究、修复、迁移或交付
scope：目标项目、模块、页面、文件或对象
hard_constraints：不能违反的业务、权限、格式和保留项
soft_preferences：可在不冲突时采用的用户或项目偏好
references：用户指定的图片、页面、文档和既有决定
acceptance：能观察或验证的完成条件
mode：AUTO、TEAM 或 SOLO
explicit_team：用户点名的 `*-team`；没有则为空
explicit_skill：SOLO 时用户点名的 Skill；没有则为空
unknowns：仍会改变路线的未知项
route_confidence：high、medium 或 low
```

白话、拼音和错别字只在理解层归一。商品码、条码、金额、规格、路径、网址、命令、版本、哈希和报错继续保留原文。不要伪造小数置信度；用 `high / medium / low` 表示路由证据强弱。

## 已有项目先做最小 Project Context Pack

只有任务涉及现有项目时才读取项目。目标是找到足以正确委派的信息，不是总结整个仓库：

1. 项目及产品目的、当前用户目标和适用规则。
2. 项目指令、README、DESIGN、技术栈清单和现有组件/Design System。
3. 当前任务真正涉及的入口、模块、调用方、数据流、测试与构建命令。
4. 不可破坏的业务流程、兼容边界、并发修改和高风险区域。
5. 下一批只有执行或验证需要时才读取的文件。

优先复用仍然有效的项目文档和已有证据。默认只在本轮上下文保留 Context Pack；项目已有对应文档时更新真实来源，只有用户明确要求才新建持久文件。上下文过时或任务范围变化时只刷新受影响部分。

## 三种模式

- **AUTO（默认）**：用户只说目标，`chanyong` 自动选最短完整 Team 或单 Skill，并直接推进已授权、可逆的工作。
- **TEAM**：用户点名一个 `*-team`；保持该 Team 为主组合，只在 Team 内使用必要方法。需要跨 Team 时先说明理由，用户可跳过。
- **SOLO**：用户说“只用 X”“X 单独处理”或 `--solo` 时，只用点名 Skill；缺少必要能力时说明限制，不静默加人。

用户要求“先推荐组合、让我选”时读取 `team-catalog.md` 展示选择；这是选择步骤，不是第四种模式。只查看目录时不执行任务。

模式只影响 Skill 组合，不扩大修改、发布、付费、登录或外发权限。

选定后先用四行以内说明：模式、真实英文 Team/Skill 名、中文职责、本次重点。不要展示未启用成员或内部推理。

## 角色与调用顺序

一次阶段最多：一个 Primary、零或一个 Auxiliary、零或一个 Validator。

- **Primary**：唯一拥有当前产物和修改责任，作主决策并交付结果。
- **Auxiliary**：只补一个明确能力缺口，例如视觉方向、图片、文案、架构或来源研究；不能完整重做 Primary 的任务。
- **Validator**：只依据 Task Contract、差异、真实产物和证据检查；默认不能改产物。已有修复授权时，失败项交回 Primary 做针对性修复。

标准顺序：理解目标 → 最小项目上下文 → 选 Primary → 必要 Auxiliary → Primary 执行 → Validator 检查 → Primary 最多修失败项一轮 → 停止。

## 路由置信与追问

- **high**：目标、产物、动作和范围一致，直接执行。
- **medium**：有一个最可能路线且工作可逆；白话复述选择后继续，并允许用户随时纠正。
- **low**：不同解释会改变产物、业务结果或不可逆动作；只问一个真正改变路线的问题。

不要因为缺少无关细节追问，也不要把“推荐组合”变成重复确认。

## 冲突优先级

```text
安全、法律和平台硬约束
> 用户当前明确要求
> 当前项目硬约束和业务规则
> 现有设计/架构/接口系统
> Primary 决策
> Auxiliary 建议
> 项目已确认偏好
> 用户长期偏好
> 本轮推测
> Skill 默认方法
```

低层规则不能覆盖高层规则。发现冲突时保留高层约束，并说明被舍弃的建议。

## 停止条件

满足任一项即停止扩展：

- acceptance 已获得最小充分证据；
- Validator 没有新的实质失败项；
- 针对性修复一轮后同一问题仍出现，需要新的证据或用户价值判断；
- 工具、权限或关键输入不可用；
- 新候选只重复已有方案；
- 用户暂停或跳过阶段。

探索型任务默认最多三个真实差异方向。用户明确要求更深验收时可以增加第二轮，但必须说明新增证据；不能无限“再优化”。

## Skill Receipt

复杂任务完成时用最短充分回执收尾，不要求每个字段都有内容：

```text
skill：实际英文 Skill 名
role：Primary / Auxiliary / Validator
scope：实际处理范围
read：真正读取的关键来源
changed：真正修改的产物
checks：运行或观察的检查及结果
assumptions：仍作为假设的内容
unresolved：未解决或待人工确认项
status：done / partial / blocked / skipped
```

回执必须来自真实执行。文件存在不等于加载成功，静态检查不等于运行通过，截图不证明键盘或读屏，方案不等于实现。默认不持久记录完整路由日志；只有用户明确要求评测或项目已有脱敏日志机制时才保存。

## 现有清单与版本证据

- `family-members.json` 是可安装成员清单和分组，不再维护一份重复清单。
- `skills-lock.json` 由安装工具记录当前项目实际安装来源和内容哈希；它是安装结果，不代替成员清单。
- `references/sources.md` 保存上游来源、许可证和固定提交基线。
- `references/source-manifest.json` 保存 chanyong 核心文件哈希。
- 安装包版本由 `VERSION` 和 Release 管理。

发现来源变化时先隔离审查和回归验证，再发布新版本；不直接把 `latest` 内容覆盖已安装客户。
